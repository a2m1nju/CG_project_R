# 길건너 친구들

OpenGL 기반 길건너기 게임 프로젝트입니다. 기존 게임에 서버 연결과 이동 요청 처리를 통합했습니다.

## 실행 방법

1. Visual Studio에서 `컴그프젝(찐).sln`을 엽니다.
2. **Release | x64**로 솔루션을 빌드합니다. 개발 중 동작 확인과 최종 제출 모두 이 설정을 사용합니다.
3. **Server** 프로젝트를 실행합니다.
4. 클라이언트 프로젝트의 **속성 → 디버깅**을 설정합니다.
   - **명령 인수:** `127.0.0.1`
   - **작업 디렉터리:** `$(ProjectDir)`
5. 서버를 켜 둔 상태에서 클라이언트를 실행합니다.

cd /d "C:\Users\user\Desktop\넷겜플\netgp\TermProject\CG_project_R"
x64\Release\Server.exe - 서버

cd /d "C:\Users\user\Desktop\넷겜플\netgp\TermProject\CG_project_R\컴그프젝(찐)"
set "PATH=%CD%;%PATH%"
"..\x64\Release\컴그프젝(찐).exe" 127.0.0.1 - 클라

클라이언트를 실행하려면 서버 IPv4 주소를 명령 인수로 지정해야 합니다. 명령 인수를 비우면 콘솔에 `Server IP address is required.`가 표시되고 종료됩니다. 서버 콘솔에서 Enter를 누르면 서버가 종료됩니다.

클라이언트에서 방향키를 누르면 Release 콘솔에도 `MOVE direction:` 로그가 표시됩니다. 위·아래·왼쪽·오른쪽 입력은 각각 0·1·2·3으로 표시됩니다.

## 주요 기능

- 기존 게임의 이동, 아이템, 장애물 충돌 및 점수 처리
- 서버의 이동 요청 검증과 승인 좌표 적용
- 초당 30틱의 서버 처리
- **1초마다 플레이어 위치 좌표 출력**
- 게임 재시작 시 이동 상태 초기화

```text
[TICK 30] player=1 round=1 x=0 z=-1 alive=1
[TICK 60] player=1 round=1 x=1 z=-1 alive=1
```

## 구현 범위

맵·이동 장애물·아이템은 minju 브랜치의 공유 월드 구현을 사용합니다. 서버가 지형과 아이템을 생성하고 모든 클라이언트에 같은 내용을 전송합니다. 장애물 충돌·환경에 따른 이동·사망 판정은 현재 클라이언트에서 처리하며, 다른 플레이어 표시와 결과 화면 등은 별도 연결이 필요합니다.

## 준비와 맵·아이템 로딩

1. 클라이언트 3개를 접속합니다. 콘솔에 같은 `READY_LOBBY_STATE`가 표시됩니다.
2. 각 클라이언트의 게임 창에서 R키로 준비·준비 취소를 요청합니다. 서버가 확정한 `ready=0/1`을 콘솔에서 확인합니다.
3. **3명 모두 준비해야** 서버가 minju 방식의 `WORLD_BEGIN → WORLD_LANE/ACTOR → WORLD_END`와 `ITEM_BEGIN → ITEM_ENTRY → ITEM_END`를 전송합니다. 접속만 했거나 2명만 준비한 상태에서는 전송하지 않습니다.
4. 클라이언트가 맵·아이템을 게임에 적용한 뒤 `LOADED`를 보냅니다. 서버는 3명의 완료를 확인한 뒤 `START`를 전송하고 이동을 허용합니다.

클라이언트 콘솔의 `WORLD_BEGIN`, `WORLD_LOADED`, `ITEMS_LOADED`, `START`에서 경기 번호와 로딩 개수를 확인할 수 있습니다. 초기 지형은 41줄이며, 앞으로 이동하면 서버가 추가 지형과 장애물을 전송합니다. 온라인에서는 클라이언트가 지형·아이템을 별도로 무작위 생성하지 않습니다.

아이템 획득·슬롯 전환(Z)·사용(X)·효과·바나나·보호막도 minju의 서버 동기화 경로를 사용합니다. 숫자 1~4는 테스트용 아이템 생성 요청입니다. 경기 중 재시작 요청은 거절합니다. 정식 재경기는 RESULT 단계에서 연결된 3명의 전원 동의를 확인하는 흐름으로 추후 연결합니다.

## 브랜치 통합 시 주의사항

- `origin/minju`의 `44c4d62`를 `yujin` 브랜치에 병합했습니다. 전원 준비·로딩 확인과 12바이트 공통 헤더를 유지하며, 중복 정의를 정리하고 minju의 셰이더 자원 해제 수정을 반영했습니다.
- 맵·아이템 메시지 번호와 본문 배치는 minju 기준을 유지합니다. 공통 헤더는 현재 브랜치의 **12바이트** 형식(길이·버전·종류·순번·경기 번호)을 사용합니다.
- minju의 `WORLD_ACTOR=21`을 유지하기 위해 기존 오류 응답은 **ERROR=44**로 옮겼습니다. 서버와 클라이언트를 함께 갱신해야 합니다.
- `ITEM_IDENTITY=35`는 경기 번호와 플레이어 번호를 구분하도록 **16바이트**(헤더 12 + 플레이어 번호 4)입니다. `LOADED=7`, `START=8`은 본문 없는 12바이트 메시지입니다.
- `RoundController::BeginRound()`는 전환 성공 여부를 `bool`로 반환합니다. 성공했을 때만 맵·아이템 전송을 시작하며, 시작 조건 검사는 해당 함수에서 처리합니다.
- 최초 준비와 전원 로딩 확인은 기존 `MatchCoordinator`·`RoundController`에 연결했습니다. minju 구현과의 차이는 접속 직후가 아니라 **전원 준비 후** 전송한다는 점입니다.

통신 검사: 서버를 따로 실행하지 않은 상태에서 `node tests/world_sync_integration.cjs x64/Release/Server.exe`를 실행하면 준비·취소, 전원 준비/로딩 조건, 동일 맵·아이템 수신, 아이템 생성·획득·보호막, 전원 재시작을 확인합니다.

## 서버 플레이어 생존 상태 관리

- 생존·이탈 상태의 원본은 서버의 `WorldState::Players()`입니다. `RoomState::players`와 `TransportSession::alive`는 제거했습니다.
- 참가자를 찾을 때는 `world.FindPlayer(playerId)`, 생존 여부만 확인할 때는 `world.IsAlive(playerId)`를 사용합니다. 없는 참가자와 이탈자는 생존자로 취급하지 않습니다.
- `MatchCoordinator`, `RoundController`, `RematchController`는 생성 시 `(room, world)`를 받으며, `ServerNetwork`는 `(world)`를 받습니다. 같은 서버 월드를 참조해야 합니다.
- 새 라운드의 참가자 초기화는 `RoundController::PrepareRound()`에서 처리합니다. `WorldState::Reset()`은 지형·장애물을 초기화하며 참가자 상태는 유지합니다.
- 이동·아이템 처리, 플레이어 상태 전송, `ShouldFinish()`는 같은 월드의 생존 상태를 참조합니다. 사망 후 같은 라운드의 위치·생존 통보로 부활하지 않습니다.
- 패킷 형식은 이번 변경으로 바뀌지 않았습니다. 사망 판정은 현재 클라이언트의 통보를 사용합니다. 서버 충돌 판정은 별도 연결이 필요합니다. 전원 사망 시 서버는 최종 플레이어 상태를 송신 큐에 등록한 뒤 RESULT로 전환합니다. 결과 기록·패킷·화면과 정식 재경기는 아직 연결 전입니다.

## 후속 할 일: 의존성 줄이기

- [ ] `ResultEntry`, `ResultData` 등 서버·클라이언트 공용 결과 자료형을 별도 공통 헤더로 분리한다.
- 클라이언트가 결과 자료형을 사용하려고 `Room.h`를 포함하면, 필요하지 않은 방 관리 클래스와 `Room.h`가 포함하는 `WorldState.h` 정의까지 함께 읽게 된다.
- 서버와 클라이언트가 결과 자료형용 공통 헤더만 포함하도록 정리해 서버 내부 구조에 대한 클라이언트의 컴파일 의존성을 줄인다. 공통 헤더에는 서버 방·월드 관리 헤더를 포함하지 않는다.
- 헤더를 포함하는 것만으로 서버 객체가 생성되거나 서버 코드가 실행되는 것은 아니다. 이번 할 일은 게임 동작과 패킷 형식을 유지하면서 자료형의 위치와 포함 관계를 정리하는 작업이다.
- 상태: 예정. 자료형 분리와 코드 수정은 아직 반영하지 않았다.

## RESULT 통지 연동

- 전원 사망 시 최종 플레이어 상태 다음에 FIX의 RESULT(14)를 전송합니다. 본문은 재경기 가능 여부·기록 수·이탈자를 포함한 참가자 3명의 결과이며 전체 56바이트입니다.
- 클라이언트는 현재 경기의 RESULT를 검사한 뒤 LobbyStage::Result로 전환하고 GetResult()로 기존 Room.h의 ResultData를 제공합니다. 결과 화면 담당 코드는 이 상태와 자료형을 사용하면 됩니다.
- 결과 화면 연결 전에는 현재 화면을 유지합니다. RESULT에서 기존 Ready() 검사가 이동·아이템 전송을 차단합니다. 재경기 투표·시작은 아직 연결 전입니다.
- 거리·생존 시간은 현재 서버 기록값이며 순위 정책 미확정 상태에서는 rank=0입니다. roomClosing은 전송 필드가 아니며 클라이언트에서 rematchAllowed로 판단합니다.
